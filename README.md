# Customer Transaction Service

A Spring Boot REST API for managing customer transactions. The application provides APIs to create transactions, retrieve transactions, update transaction status, and retrieve all transactions for a customer.

## Project Overview

The service implements four core transaction operations:

1. Create a transaction
2. Get a transaction by transaction ID
3. Update a transaction's status
4. Get all transactions for a customer

The application uses an H2 in-memory database and Spring Data JPA for persistence.

## 1. Create Transaction

### Request

```http
POST /api/transactions
```

### Headers

```text
Content-Type: application/json
Idempotency-Key: unique-key-001
```

### Request Body

```json
{
    "customerId": "102",
    "amount": 1500.50,
    "currency": "INR",
    "transactionType": "PAYMENT"
}
```

### Successful Response

**HTTP 201 Created**

```json
{
    "transactionId": "generated-transaction-id",
    "idempotencyKey": "unique-key-001",
    "customerId": "102",
    "amount": 1500.50,
    "currency": "INR",
    "transactionType": "PAYMENT",
    "transactionStatus": "PENDING",
    "createdAt": "2026-09-01T18:20:15.123"
}
```

### Behaviour

- The transaction ID is generated by the server.
- The idempotency key is used to prevent duplicate transaction creation.
- Every newly created transaction starts with `PENDING` status.
- `createdAt` is automatically generated when the transaction is created.

If the same idempotency key is submitted again, the existing transaction is returned.

## 3. Update Transaction Status

### Request

```http
PATCH /api/transactions/{transactionId}/status
```

Example:

```http
PATCH /api/transactions/abc-123/status
```

### Request Body

```json
{
    "status": "COMPLETED"
}
```

### Successful Response

**HTTP 200 OK**

```json
{
    "transactionId": "abc-123",
    "idempotencyKey": "unique-key-001",
    "customerId": "102",
    "amount": 1500.50,
    "currency": "INR",
    "transactionType": "PAYMENT",
    "transactionStatus": "COMPLETED",
    "createdAt": "2026-09-01T18:20:15.123"
}
```

### Status Values

The supported transaction statuses are:

```text
PENDING
COMPLETED
FAILED
CANCELLED
```

### Status Transition Rules

A transaction can change status only while it is `PENDING`.

Allowed transitions:

```text
PENDING → COMPLETED
PENDING → FAILED
PENDING → CANCELLED
```

Once a transaction reaches `COMPLETED`, `FAILED`, or `CANCELLED`, further status changes are rejected.

An invalid status transition returns **HTTP 409 Conflict**.

# Transaction Model

Each transaction contains the following fields:

| Field | Description |
|---|---|
| `transactionId` | Unique transaction identifier generated by the server |
| `idempotencyKey` | Key used to prevent duplicate transaction creation |
| `customerId` | Identifier of the customer |
| `amount` | Transaction amount |
| `currency` | ISO 4217 currency code |
| `transactionType` | Type of transaction |
| `transactionStatus` | Current transaction status |
| `createdAt` | Timestamp automatically generated when the transaction is created |

## Transaction Types

The supported transaction types are:

```text
PAYMENT
TRANSFER
REFUND
```

# Validation Rules

The API validates transaction input before processing it.

### Customer ID

- Required
- Maximum 50 characters
- Allows letters, numbers, `_` and `-`

### Amount

- Required
- Must be greater than zero
- Maximum 2 decimal places

Example of a valid amount:

```text
1500.50
```

### Currency

- Required
- Must be a valid ISO 4217 currency code
- Three-character currency code

Examples:

```text
INR
USD
EUR
GBP
```

### Transaction Type

Required.

Allowed values:

```text
PAYMENT
TRANSFER
REFUND
```

### Transaction Status

For status updates, the value is required.

Allowed values:

```text
PENDING
COMPLETED
FAILED
CANCELLED
```

## Assumptions and Limitations

* Initially, I followed the assignment by accepting the Transaction ID from the client and checking for duplicate IDs. Later, I changed this to a more realistic approach where the **server generates the Transaction ID** and sets the initial status to `PENDING`.
* An **Idempotency-Key** is required when creating a transaction and is used to prevent duplicate transaction creation.
* H2 is used as an in-memory database for this exercise.
* Only transitions from `PENDING` to `COMPLETED`, `FAILED`, or `CANCELLED` are allowed.
* No authentication or authorization has been added because it is outside the scope of this exercise.
* The application is designed as a simple REST service and does not include additional infrastructure such as messaging, caching, or an external production database.

# Future Improvements

If this service were developed further for a production environment, possible improvements could include:

- Persistent production database configuration
- Authentication and authorization
- API documentation using OpenAPI/Swagger
- Database migrations
- More detailed logging and monitoring
- Additional integration tests
- A more robust idempotency mechanism for production use. The current implementation uses the `Idempotency-Key` to return the existing transaction when the same key is received again. A production implementation could further improve this by storing and managing idempotency keys with request details and handling concurrent duplicate requests safely.

These improvements are intentionally outside the current scope to keep the implementation simple and focused on the required transaction operations.
